# 送药巡诊机器人：赛事功能差距分析与修改方案

> 依据《2025 中国机器人大赛医疗机器人赛项送药巡诊机器人项目竞赛规则》及当前仓库代码核查。
> 核查日期：2026-09-23。结论只代表代码和启动文件的现状，GPIO、CAN、摄像头、音频和赛场实测仍需单独验收。

## 一、评分目标与结论

| 项目 | 分值 | 当前判断 | 主要依据 |
|:---|---:|:---|:---|
| 1 床巡查、药箱开启 | 20 | 流程已编排，实机待验 | `mission_controller.cpp`、`open_medicine_box.cpp` |
| 1 床摆药、语音 | 25 | 有流程，但条码/机械臂/TTS闭环未证实 | `mission_controller.cpp`、`arm_and_gripper_node.cpp`、`speak_node.cpp` |
| 1 床音视频 | 20 | 节点存在，必须完成双端设备和 `/Ready` 联调 | `audio_chat_node.cpp`、`video_stream_node.cpp` |
| 3 床巡查、药箱开启 | 20 | 流程已编排，路径和硬件待验 | 同上 |
| 3 床摆药、语音 | 25 | 有流程，但条码分配存在确定性缺陷 | `barcode_qr_detector.cpp` |
| 3 床音视频 | 20 | 同上 | 音视频 launch |
| 回到起始区 | 20 | 有里程计和保守外接圆校验，参数未实测 | `mission_controller.cpp` |
| 两床条码正确显示并持续保留 | 10 | 当前不能判定满足，显示协议和扫码逻辑均需修复 | `display_node.cpp`、`barcode_qr_detector.cpp` |

当前最重要的结论：代码已经具备完整任务状态机、物理按钮、急停、VL53 安全停止和保守入圈校验，但“能编译/能启动”不等于“能得分”。目前至少有 4 个比赛前必须关闭的阻断项：条码流水线、启动合规、实体屏幕双行显示、音视频和语音的真实设备验收。

## 二、已经具备的能力

### 1. 任务状态机和计时

`mission_controller` 已覆盖护士台扫码、两床顺序导航、床边微调、开箱、摆药、语音、回归和结束显示；全局超时默认 180 秒，阶段超时默认 30 秒。 `cmd_vel_mux` 支持 `/chassis_lock`，开箱到语音阶段可以强制输出零速度。

但这些是“流程骨架”，服务返回成功、路径完成、药品真实到位和语音真实播出仍依赖外部节点和硬件反馈，不能仅凭 ROS 日志验收。

### 2. 启动按钮和急停节点

- `start_button_node.cpp` 已实现 GPIO 17 轮询、50 ms 去抖和 LED 输出。
- `emergency_stop_node.cpp` 已实现 GPIO 22 轮询，并向 `/emergency_stop` 发布状态。
- `cmd_vel_mux_node.cpp` 收到急停或底盘锁时直接发布零速度。

这解决了“完全没有节点”的问题，但还没有解决赛事合规和故障安全问题，见第三节。

### 3. 距离安全和入圈校验

`vl53l1x_can_bridge` 已发布前、左、右三路 `sensor_msgs/Range`，并有数据新鲜度、序号、无效帧和诊断信息；`distance_safety_node` 会在前方距离超时或过近时占用 mux 的最高优先级安全通道。任务状态机用车体/整机外接圆和三路 VL53 数据检查床边圆圈及起始区。

当前仍是“停止保护”，不是“绕障导航”。外接圆半径、传感器安装方向和 300 mm 圆圈坐标必须用实车测量后再确认。

## 三、必须优先修复的阻断项（P0）

### P0-1 条码检测和床位分配不闭环，直接影响 10 分和两床任务

发现了以下确定性问题：

1. `BarcodeQrDetector::init()` 只初始化了 `qr_scan_start_time_`，没有初始化 `barcode_scan_start_time_`。该时间保持零值，第一次收到图像时条码计时会立即超时，并发布两个空条码。
2. 检测器把第一条条码固定发布到 `/barcode_bed1`，第二条固定发布到 `/barcode_bed3`，没有根据 QR 决定的首床和次床分配。QR 首床为 3 时，任务状态机会等待 `/barcode_bed3`，但第一条被错误发到了 `/barcode_bed1`。
3. 超时发布的空字符串也会让状态机把 `barcode_*_received_` 置为 true；`verifyBedNumber()` 只检查“收到过哪个话题”，不检查条码非空、格式或是否为当前床的有效值。
4. 检测器的 `barcode_bed*_detected_` 是节点生命周期状态，没有按一次比赛或一次床边任务重置，重复比赛可能无法重新扫描。

修改要求：

- 进入床边扫描时由任务状态机发布当前目标床/扫描会话（建议新增 `scan_target_bed` 和 `scan_session_id`），检测器只向当前目标输出结果。
- 在初始化、每次新任务和每次换床时重置条码计时和检测状态；计时从进入 `SCAN_BARCODE_*` 开始，而不是从节点启动开始。
- 空字符串、非法长度、非允许编码必须判为失败或继续等待，不能当作成功。
- 持久显示只写入通过校验的真实值；记录床号、原始值、时间戳和扫描会话，便于赛后追溯。
- 增加两种顺序（1→3、3→1）和重复比赛的自动化测试。

### P0-2 启动信号存在违规入口和重复入口

`mission_complete.launch` 默认同时启用 GPIO 物理按钮和 CAN 启动转发。 `mission_controller` 对 `/start_signal` 不区分来源，任何能发布该话题的节点都可以启动任务。两个启动节点还使用 latched publisher，启动后新订阅者可能立即收到旧启动信号。这与“只能按车体物理按钮启动”的赛规不一致。

修改要求：

- 比赛 launch 默认 `enable_can_start_signal:=false`，只保留 GPIO 按钮；CAN 入口只用于台架调试。
- GPIO 导出失败时比赛节点应 `required=true` 并退出，不能继续运行并声称可依赖手动话题。
- `/start_signal` 改为非 latched、单次脉冲；任务控制器增加启动来源认证或改用私有硬件节点服务，禁止 `rostopic pub` 直接作为比赛入口。
- 加入“按钮按下、任务只启动一次、释放后再次按下才允许下一局”的实机验收记录。

### P0-3 屏幕并未真正满足“两行持续显示”

`mission_controller` 虽然拼接了 `1床条码...\n3床条码...`，但 `display_node` 目前把整段文本当作一个字符串：

- CAN 输出最多发送 14 个字节，超出部分被截断；
- 中文是 UTF-8 多字节，按字节截断可能形成乱码；
- 没有解析换行、行号、清屏和持久页面；
- `barcode_qr_detector` 还会先后发布覆盖式的单行/拼接文本，可能覆盖任务状态显示。

修改要求：定义明确的屏幕协议（行号、编码、长度、结束/清屏），屏幕节点维护两个锁定的条码行和其他状态行；条码成功后只更新对应行，直到下一局显式清屏。必须在真实 LCD 上验证“无需按键切页、回到起始区后仍显示两行完整数值”。

### P0-4 音视频和语音只能算“软件存在”，不能算得分闭环

音视频节点依赖两端摄像头、PulseAudio/pacat、Opus、固定 IP 和 `/Ready=1`。 `mission_complete.launch` 只启动节点，不自动建立医生端链路，也没有把通话状态纳入任务状态机。必须确认比赛时两端的 ROS master、IP、端口、摄像头话题和音频设备均可用。

语音节点在没有 espeak/festival 时会把“日志输出”当作成功返回：`speak_node.cpp` 中 `res.success = true`。这会让状态机误以为已经播报并继续流程，现场却没有声音。

修改要求：

- 音频输入、播放、视频帧和 `/Ready` 状态加入健康检查；任一端未建立真实流时显示失败，不得只看服务返回值。
- TTS 无可用引擎、播放失败或设备不存在时返回失败；任务状态机记录“播报开始/完成”时间戳，不能以日志代替声音。
- 对 1 床、3 床分别做“同时听到声音并看到对方画面”的录像或验收记录。

## 四、重要缺口（P1）

### 1. 动态障碍物仍未形成比赛默认方案

默认 `use_dynamic_navigation=false`，实际运行的是 YAML 固定路径 + `path_tracker`；`distance_safety` 只会减速/停车，不会绕行。动态模式虽然提供 AMCL、move_base 和 TEB 配置，但要求外部地图和 `/scan`，默认 map 路径是占位值，当前仓库没有可直接参赛的激光雷达输入和地图。

两种可选方案必须择一并实测：提供完整地图、激光雷达、TF、AMCL 初始位姿和 move_base 参数，验证随机障碍物绕行；或采用安全停车、人工处置和重新启动策略，并明确承认不能保证绕障得分。

### 2. 急停是软件停速，不是硬件断能；释放策略也不安全

急停节点已经存在，但 GPIO 失败时 launch 设置为 `required=false`，可能在无急停的情况下继续比赛。另有 `health_monitor` 和 `emergency_stop_node` 两个发布者共同写 `/emergency_stop`；`health_monitor/reset` 会发布 false，物理急停释放也会发布 false，mux 没有“急停触发后必须重新按启动才能运行”的锁存逻辑。

修改要求：常闭急停串联电机电源继电器，软件话题只作第二层保护；GPIO 初始化失败时比赛模式退出；急停触发后锁存，只有明确的人工复位和新一轮物理启动才能解锁。

### 3. 健康监控目前检查的是“有发布者”，不是“数据正常”

`health_monitor.cpp` 通过 ROS master 查询话题发布者数量，把“存在发布者”直接视为活跃，没有订阅 `/odom`、电机状态、VL53 或路径数据并检查时间戳。它也不会在关键话题失效时自动锁停，只会生成报告。因此 CAN 断线、数据冻结或传感器发布旧值可能被误判为正常。

修改要求：按消息时间戳和序号检查新鲜度；监控 CAN 心跳、里程计、三路 VL53、路径完成和音视频状态；关键项失效时触发不可自动清除的安全锁，并在屏幕/诊断中显示具体原因。

### 4. 状态机的“超时跳过”会跳过计分动作

阶段超时后，`SCAN_QR`、两次入圈和两次条码扫描会直接跳到下一状态；`HOME_CHECK` 超时还会直接进入 `STOP`。这能提高联调时的可继续性，但比赛时可能在未扫码、未入圈或未显示正确条码的情况下继续执行，形成“流程结束但不得分”的假成功。

修改要求：联调模式和比赛模式分离。比赛模式对 QR、入圈、条码、开箱、摆药、播报使用 fail-closed；超时进入安全停止/回归策略并明确记录失分，只有导航回归可以在确认安全后尝试降级。

### 5. 入圈模型仍是保守外接圆，不是整机真实投影

当前检查只使用 `base_projection_radius_m` 或 `full_projection_radius_m`，没有机械臂姿态、药箱盖、夹爪和传感器安装偏置的多边形模型。参数默认值还分别出现在 `mission_params.yaml`、`navigation_params.yaml` 和 launch 中，存在配置漂移风险。

修改要求：统一参数唯一来源；实测底盘和机械臂各姿态投影，使用 footprint/polygon 校验；记录床 1、床 3、起始白框三组标定结果。

## 五、尚未接入的赛事功能（P1/P2）

### 心率和体温

`patient_measurement_interface.launch` 明确是空占位文件，`mission_complete.launch` 默认 `enable_patient_measurement=false`。当前没有设备驱动、消息订阅、测量时序、显示和结果存档，因此不能宣称已支持心率/体温。接入时必须提供真实驱动 launch、消息类型、超时/无效值处理和状态机验收；不能用假节点占分。

### 构建和部署可重复性

`robot_navigation/CMakeLists.txt` 在未找到 Opus 时仍无条件定义 `HAS_OPUS`，但源码会包含 `<opus/opus.h>`；不同机器上可能直接编译失败。 `package.xml` 也没有声明系统级 `libopus-dev`、zbar、pacat、espeak、usb_cam 等安装前置条件。

修改要求：CMake 只有在检测到 Opus 头文件和库时才定义 `HAS_OPUS`；在 README 或部署脚本中固定依赖版本，并提供一次从干净工作区构建、启动和设备自检的记录。

## 六、建议实施顺序

1. 修复条码计时、目标床分配、空值校验、会话重置，并用 1->3/3->1 两种 QR 顺序回放图像测试。
2. 制作比赛专用 launch：只允许物理按钮；急停和底盘 CAN/GPIO 初始化失败即退出；关闭所有手动启动入口。
3. 落地 LCD 双行协议，验证 UTF-8/行长度、锁定显示、清屏和跨节点消息覆盖关系。
4. 固化机械臂、药箱 CAN、TTS、摄像头、PulseAudio、Opus、医生端 IP 的设备清单，完成两床端到端演练。
5. 将比赛模式的关键阶段改为 fail-closed，修正急停锁存和健康监控数据新鲜度。
6. 决定并实测动态绕障方案；没有地图和 `/scan` 实测数据前，不要把 `use_dynamic_navigation=true` 当作可用能力。
7. 最后接入真实心率/体温设备，并进行完整 3 分钟计时和异常恢复演练。

## 七、比赛前验收清单

- [ ] 只能按车体物理按钮启动；CAN、键盘、鼠标、`rostopic pub` 均不能启动。
- [ ] 急停按下后电机硬件断能或至少不可被任何 ROS 节点自动解除；复位必须重新物理启动。
- [ ] QR 四种合法顺序均能得到正确的首床、首箱、次床、次箱。
- [ ] 两床条码均是真实非空值，床位分配正确，重复开局可重新扫描。
- [ ] 回到起始区后 LCD 无需切页即可持续显示两行完整条码。
- [ ] 开箱、摆药、播报全过程底盘锁定，语音在摆药完成后 5 秒内真实播放。
- [ ] 1 床和 3 床都能同时建立双向音频和视频，且记录 `/Ready`、帧率、音频设备状态。
- [ ] VL53 三路数据新鲜；传感器断线、CAN 断线、里程计冻结会进入安全状态。
- [ ] 随机障碍物方案经过实车测试，或明确采用停车降级策略并评估扣分。
- [ ] 从干净环境安装依赖、编译、启动和重启任务均成功；总流程在 180 秒内完成。
