# STM32 CAN 回传故障修复提示词

请在实际 STM32 工程中修复“电机反馈已经恢复，但运行数秒后 CAN1 发送失败计数增长，ROS 锁存保护停车”的问题。请直接检查代码、实施修复、补充回归测试并生成可烧录固件，不能只给建议。

## 已知实测证据

- STM32F407，电脑通过 CANable 接 CAN1，电机驱动器接 CAN2。主机 can0 使用 500 kbit/s、采样点 83.3%、SJW=1。
- 四个电机地址 1、2、3、4。ROS 逻辑轮到 STM32 索引映射为 [1,0,3,2]，方向符号均为 1。
- 修复接线等问题后，6 秒内 60 次心跳全部收到成功应用应答；四路均收到真实扩展 0x35 速度和 0x3A 状态回包，最后为 0 RPM、flags=0x83。不能把 0x83 当成故障。
- 启动现有 ROS CAN 节点，max_rpm=10，没有发布非零目标，约 7 秒后触发 `STM32 queue/execution/transport failure counter changed`。
- 随后的 3 秒窗口中，0x103 第三类诊断的 CAN1 TX failure 从 9605 增至 9659；CAN2 TX failure 保持 56，stop failure 保持 0。入队丢弃保持 56，响应超时保持 1，执行失败保持 0。历史非零值不能当成本窗口新增故障。
- 节点还记录过 `CAN error class=0x0C, controller flags=0x00, protocol=0x10, location=0x00`。短窗口无错误不代表持续稳定，Linux 本地 echo 不代表远端收到。
- 临时将 report_mask 从 7 改为 5，保留基本状态和速度，12 秒内心跳成功 120 次、无 CAN 错误且就绪为 true；但约 16 秒仍再次出现协议错误和保护停车。减少报文量没有根治故障。

## 请重点检查并实施

1. 先读实际 can_transport.c/.h、main.c、stm32f4xx_it.c、can_protocol.c、zdt_can_driver.c、motor_control.c 与测试。核对诊断字段与运行固件版本；不能仅凭上述计数认定软件队列、CANable 或电气线路是唯一根因。
2. 原源码 CAN1 发送采用 64 帧共享 FIFO，周期状态/位置/速度、距离、统计、原生驱动反馈和命令 ACK 共用队列。检查生产速率、突发长度、任务调度、HAL_BUSY、HAL_CAN_AddTxMessage 失败、邮箱状态和队列满的实际原因。
3. 对可替换的周期快照实行“同一 CAN ID + 报告类型 + 电机/传感器编号只保留最新待发值”，避免旧快照持续积压。可以给可靠 ACK/事件/真实反馈预留容量，容量和延迟要通过测试证明。不要合并命令、命令 ACK、实体按钮事件、急停事件、一次性错误诊断或多包协议。
4. 若周期生产者遇到背压，应明确保留/更新待发数据；区分“尚未接收、可以重试的周期数据”与“已接受关键帧丢失、真实 HAL 发送失败”。禁止清零、冻结失败计数，禁止忽略错误帧或放宽 ROS 安全判断来掩盖问题。
5. 统计应能区分队列满、HAL 提交失败和硬件 CAN 错误；检查 ACK、错误被动、Bus-Off、RX overrun 和重传。诊断应兼容现有 0x103 字段；需要扩展时另行说明新格式与 ROS 配套改动。
6. 检查临界区、ISR/任务并发、环形缓冲回绕、取消发送与回调，不允许忙等或阻塞电机控制任务。确认硬件发送完成的判据，不把邮箱提交成功当成远端应用应答。
7. 核实实际 HSE、PCLK1 和 CAN 位时间；参考源码为 HSE=8MHz、PCLK1=36MHz、Prescaler=6、BS1=9TQ、BS2=2TQ，即 500 kbit/s。不要未经硬件核对就修改时钟。
8. 保持 0x100 标准命令、0x101 状态、0x102 ACK、0x103 统计和 CAN2 电机协议兼容；保持轮序、限速、急停、心跳超时、反馈新鲜度、碰撞保护和实体启动联锁。不要伪造按钮或通过原生运动透传绕过联锁。

## 验收与交付

- 先用回归测试复现周期突发/邮箱暂满时的拥塞，再验证最新值合并、关键帧预留、真实失败上报、恢复后的有序发送、环形回绕以及急停优先处理。原有运动协议、安全和传感器测试继续通过。
- 生成明确的 ELF/HEX/BIN，给出构建命令、文件路径和校验值。主机模拟测试与实际烧录/硬件测试分别报告。
- 烧录后先不发运动，连续观察至少 60 秒：四路原生速度/状态持续新鲜、心跳应答正常，诊断无新增失败、无 CAN 错误、ROS 持续就绪。未达到就继续定位，不进入运动阶段。
- 稳定后保持车轮架空，准备 10 RPM、约 1 秒的点动，由实体启动键触发；检查真实运动反馈与运动 ACK，随后发送零目标并通过四路新回包确认停车。失败立即执行现有停车流程。
- 说明已证实的根因、具体改动、测试结果、未验证项。如果物理协议错误仍存在，要保留并报告证据，不能声称软件修改已彻底修复。

补充：ROS 工作区曾有一个未烧录的候选实现，新增 can_transport_send_latest，合并周期状态/距离/统计并预留 8 个队列槽。它是待审查方案，不是已经完成实机验收的修复。请以实际 STM32 工程内容为准；如果已包含候选修改，继续审查与验证，避免重复实现。
