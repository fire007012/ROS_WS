# CAN CRC 根因分析（2026-10-15）

现有证据把故障范围定位到 CANable 与 STM32 CAN1 所在的上游 CAN 总线。
CRC、格式、位填充错误属于 CAN 控制器报告的位流异常；ROS 发送拥塞和重连缺陷可以放大故障，
但不能单独解释这些错误。尚无实测证据能指定某根线、某个收发器或某个时钟是唯一根因。

## 已核对的证据

| 证据 | 能说明什么 | 不能说明什么 |
| --- | --- | --- |
| `2000000C [8] 00 30 00 08 00 00 00 00` | 控制器问题与协议错误；错误位置报告为 CRC sequence | 没有原始受损帧、发送节点 ID 或示波器波形，无法定位坏线或器件 |
| 同时出现 `data[2]=02`、`04` | 另有格式、位填充错误，符合位流接收/同步异常 | 错误标志也可能使其他节点观察到后续错误，不能当成三个独立根因 |
| `data[1]=30` | 按 SocketCAN 定义包含 RX/TX passive 标志 | 无实际 TEC/REC，不据此断言两个计数都达到阈值；适配器固件的状态编码也需考虑 |
| 10 月 8 日运动通过时，warning 278→350、passive 19→25 | 成功控制电机时链路已经存在错误 | 当天没有同样的 CRC 原始抓包，不能断言每一次状态变化都是 CRC |
| 首次传感器读取时 ERROR-PASSIVE，RX dropped/overrun=0 | 软件接收队列溢出不是这次状态的直接证据 | RX packets 包含错误帧；TX=0 表示没有统计到完成的发送，不能证明没有发送尝试 |
| `Couldn't set bittimings (err=-110)` | CANable 的 USB 控制请求超时，存在独立的适配器/USB/虚拟机问题 | 不能直接解释 CAN 线上 CRC，不能把 USB CRC 和 CAN CRC 混为一谈 |
| USB 多次 disconnect | 适配器曾离开虚拟机 | 不知道是否人工拔插/切回宿主机，不能称为自发掉线 |

错误帧释义核对自 `/usr/include/linux/can/error.h`。错误帧中的 CRC sequence 是错误位置字段，
不是 ROS 负载中某个校验字节。CAN 外设在实际发送时计算 CRC；应用改变数据、标准/扩展帧或 DLC，
通常会得到另一帧 CRC 合法的数据，接收应用可能拒收，但不会因此自动成为 CAN CRC 错误。
正常仲裁和正常高负载本身也不应产生 CRC/位填充错误。

## 位时序核对

读取的是 `/tmp/stm32-remove-estop-before/` 源码快照，不能据此证明当前芯片内烧录版本相同。

- `main.c`：HSE 假定 8 MHz，PLLM=8、PLLN=144、PLLP=2，SYSCLK=72 MHz，APB1 分频 2。
- bxCAN 使用 PCLK1=36 MHz，不使用 APB1 定时器的倍频时钟。
- CAN1/CAN2：Prescaler=6、BS1=9、BS2=2、SJW=1。
- 位速率为 `36 MHz / (6 × (1+9+2)) = 500 kbit/s`；采样点为 `10/12 = 83.33%`。
- 先前 Linux can0 为 500 kbit/s、采样点 87.5%。采样点不同是允许的，不能直接认定配置错误。

因此，没有发现这份源码中确定的位速率计算错误。实际晶振、RCC/BTR 寄存器及固件版本仍未读回。
旧测试能双向控制电机，使严重固定速率失配的解释较弱，但不排除新烧录版本或边缘同步问题。

## 值得优先核实的具体接线问题

本轮用户补充：STM32 使用独立电源口或仅 USB 电源两线；CAN_TTL 为 BESTEP 品牌，供电 5 V。
因此，外部 USB 数据线与 PA11/PA12 冲突的假设先排除。BESTEP 是模块品牌，不能代替芯片型号。

1. **CAN1 的终端和参考地。** 在整段总线断电后测 CAN_H—CAN_L：两端各一个 120 Ω 时通常约 60 Ω；
   约 120 Ω 提示只有一个，约 40 Ω 提示可能有三个，近开路提示可能缺失。
   读数受实际电路影响，不能只凭 60 Ω 就认定信号合格。非隔离收发器还需确认两端参考地及地电位差。
   若模块自带 120 Ω，外加电阻必须一起计数；CAN1、CAN2 分别计算，不能把两段总线的电阻混在一起。
2. **CAN1 收发器的实际型号、供电和工作模式。** BESTEP、5 V 不足以核对芯片的额定供电和控制引脚。
   若是 TJA1050，5 V 通常是正常供电；若是额定 3.3 V 的收发器且模块没有稳压，情况则不同。
   不能因为 MCU 为 3.3 V 就认定 5 V 模块不兼容，也不能未经型号核对把模块供电改为 3.3 V。
   源码快照没有控制收发器 STB/EN。接线文档中“可能需要拉高 STB”不能直接照做：
   许多器件 STB 高反而进入待机，SN65HVD230 则有不同含义的 Rs 引脚。必须依据具体型号确认。
3. **线束、收发器和电源的实测。** 错误组合支持优先检查信号完整性和同步裕量，但没有波形，
   不能区分反射、干扰、接触不良、收发器异常和时钟偏差。需要下面的单变量验证。

上述是排查顺序，不是已证明的概率排序。CAN2 电机侧可能通过电源/地噪声影响上游，
但 can0 错误帧不能直接证明 CAN2 某个电机在发坏帧。CAN1、CAN2 按设计应为两段独立总线。

## 恢复硬件后，如何收敛到根因

先在无运动命令的条件下，保留 CANable 与 STM32 CAN1 的最小链路和正确终端。
普通 candump 进程不发应用帧，但正常模式的 CANable 仍会自动 ACK；不要误切 listen-only 造成缺 ACK 重发。
每组使用相同的固定窗口，保存带时间戳的错误帧、有效帧和前后接口统计。

| 单变量验证 | 结果如何解释 |
| --- | --- |
| 换已知正常的短双绞线、核实终端；只保留两个节点 | 若错误随原线束或终端配置恢复，可定位该环节 |
| 保持线束/STM32不变，换已知正常 CAN 适配器 | 区分适配器端与 STM32/线束端；USB切换本身恢复状态不等于适配器损坏 |
| 最小链路仍错，示波器同时看 CAN_H/L、STM32 TXD/RXD 及收发器电源 | TXD 正常而总线/RXD 失真偏向收发器/布线/供电；TXD 位宽异常再核实实际时钟/BTR |
| 最小链路正常，逐项接回电机侧、传感器、舵机电源 | 找到噪声、地电位差或供电瞬态的触发条件；电机运行测试需另行安排 |

500 kbit/s 名义位宽为 2 μs；波形中相邻边沿间隔可为多个位宽，不能把任意边沿间隔直接当成一个位。
必要时读回 STM32 RCC、CAN1 BTR/ESR（TEC、REC、LEC），与适配器同期记录对照。
