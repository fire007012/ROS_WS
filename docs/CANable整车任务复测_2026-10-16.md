本次用户确认四轮架空、整车供电且四个电机驱动器均亮灯。尝试启动整车任务，

底盘节点锁存急停。此前“ACK 问题已解决”的历史说明不能替代本轮结果。

- 临时覆盖轮速上限 20 RPM、平移上限 0.10 m/s、转向上限 0.35 rad/s、
  平移/转向加速度上限 0.10 m/s²、0.20 rad/s²；没有修改生产参数或路线文件。
- 本机无摄像头、串口测量设备，关闭相机、音视频、体征接口和 GUI。

## 实机结果（北京时间）

18:45:36 首次启动后，四轮真实反馈缺失，底盘约 2 秒后锁存急停。
随后原生电机回包恢复，采样得到四轮速度均为 0 RPM、状态均为 `0x83`，
`/odom` 恢复约 50 Hz。调用健康复位服务返回成功，但 CAN 节点明确拒绝复位，
因此没有把服务返回成功认定为底盘已就绪。

关闭第一轮所有控制进程，再次独占启动。18:50:08 记录速度缓存准备完成；
8 秒采样内得到约 50 Hz 里程计、约 35 Hz 电机状态发布，
`/motor_link_ready=true`、`/robot_state=CACHE_READY`、任务状态为 `IDLE`，
CAN 诊断当时为正常。缓存准备完成不代表已实际运动。

随后 5 秒被动抓包捕获：

| 报文 | 本轮证据 |
| --- | --- |
| SocketCAN 错误帧 | ID `0x2000000C`，DLC=8，`00 00 10 00 00 00 00 00` |
| STM32 第三类统计 | 标准 ID `0x103`，`03 03 09 00 00 00 00 00` |
| 停车命令 ACK | 标准 ID `0x102`，cmd=`0x03`、result=`0x00` |
| 心跳 ACK | 标准 ID `0x102`，cmd=`0x09`、result=`0x00` |

此前采样的第三类统计为 `03 02 09 00 00 00 00 00`，CAN1 发送失败计数
从 2306 增为 2307。18:50:26.381 底盘节点记录：
`ESTOP latched: STM32 queue/execution/transport failure counter changed`。

本次尝试通过 `/select_path` 预加载真实 `nurse_station` 路径，但此时底盘已锁存急停，
没有进入实体启动、护士台到达或后续路线验证。没有通过复位重试运动来覆盖这次故障。

最终 CAN 节点诊断：`can_error_frames=9`、`bit_errors=1`、
`last_protocol_error=16`、CRC/格式/位填充错误均为 0。
抓包中另外 8 条 `0x20000004`、控制器标志为零的报文属于状态通知，
不能把 9 条全部称为独立协议故障。
`protocol=0x10` 是隐性位发送错误，不据此认定为 CRC 错误或指定单一硬件根因。
最终接口仍显示 ERROR-ACTIVE，内核 error-warning/passive/bus-off 计数为 0；
这些快照不否定采样期间实际捕获的协议错误。

## 按用户要求仅处理 ROS 端的后续修复

用户随后明确限定只排查和修改 ROS 端。本轮未修改接口位时序、硬件或 STM32 固件。

缩小测试范围后，仅启动生产 CAN 接口节点，不启动规划器、不提供运动目标，
仍在约 78 秒后复现 `protocol=0x10` 及 STM32 发送失败计数变化，随后又出现一次。
故障因此不依赖路径跟踪、机械臂动作或电机转动。另做的 30 秒被动监听没有记录
错误或统计变化；短时间未复现不能单独证明物理链路长期无故障。

ROS 代码中确认：原生查询每 50 ms 无条件发送，而 STM32 本身也在转发四轮
原生 `0x35/0x36/0x3A` 回包。查询和对应回包使用同一个扩展帧 ID
（`0x100/0x200/0x300/0x400`），但 DLC/负载不同。如果两端同时以同一 ID 发送，
它们不能通过 ID 仲裁区分，后续不同位可能触发位错误。这与捕获的隐性位错误
一致，是本轮处理的 ROS 侧冲突风险；没有示波器或固件内部跟踪，不能据此断定
每次错误都唯一由这一机制引起。

已修改 `can_motor_interface`：

- 优先使用已收到的真实原生反馈，某轮速度或状态在过期时间的一半仍无新样本时
  才补查。默认 0.5 秒补查、1 秒过期停车；轮序公平调度，每次最多发送一条查询。
  `0x101` 缓存、心跳或统计均不能更新真实原生反馈时间。
- 增加 `link_health_issue`、逐轮速度/状态年龄、配置 ACK 状态及心跳 ACK 年龄，
  明确区分配置未确认、某轮缺回包、统计过期等原因。
- 固件统计变化日志记录具体字段和前后数值；例如
  `can1_tx_failure: 2306 -> 2307`，不再只有笼统的队列/执行/传输错误描述。

验证结果：

- 对照抓包：旧节点 30 秒发送 600 条额外原生查询；最终修改后的节点在同样
  30 秒内发送 0 条原生查询，四轮原生反馈仍正常，心跳保持 10 Hz。
- 最终修改后的独立 CAN 节点连续运行约 156 秒，日志无 ERROR；采样诊断中
  CAN 错误、I/O 错误、拥塞均为 0，`/motor_link_ready=true`，四轮为 0 RPM。
  各轮状态样本实际间隔可超过 0.25 秒，最终使用过期时间一半作为补查阈值。
- 随后同一临时限速配置启动 17 个整车业务节点，连续待机约 121 秒，
  CAN 错误、I/O 错误、拥塞均为 0，STM32 CAN1 发送失败计数保持 2309。
  退出前采样 `/motor_link_ready=true`、`/robot_state=CACHE_READY`、任务 `IDLE`，
  四轮为 0 RPM，里程计位置和速度均为零。本轮没有按实体启动键或选择运动路线。
  整车启动后的 30 秒抓包仅有 3 条原生补查，真实反馈主要来自 STM32 正常转发。
- 编译成功，21 项协议/链路单元测试及 17 项真实节点故障注入测试全部通过。
  故障注入测试拦截所有 PF_CAN 调用，不向实车发送故障或运动。
  覆盖新鲜原生回包抑制补查、缺少单项反馈时补查、缓存不能隐藏失联、
  拥塞/掉线停车、F6 ACK 过期、急停互锁和故障计数变化。

这些结果验证了 ROS 侧静止通信改进，不能替代实际运动、扫码、定位和放药的完整任务验收。
六路测距仍上报 `I2C_ERROR`，无效状态来自收到的真实 CAN 数据，未在 ROS 中替换为有效值。
最终已退出本轮所有控制节点和测试 master。
